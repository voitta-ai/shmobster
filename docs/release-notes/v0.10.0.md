One issue: the dependencies are a lock now, with hashes, and CI notices the next
stale one. Short operator to-do, but it is not zero -- the install command
changes and three packages move.

## What an upgrade requires

**Reinstall with `--require-hashes` (#152).**

    git pull && .venv/bin/pip install --require-hashes -r requirements.txt

`requirements.txt` used to be five unpinned `>=` lines. It is now generated from
`requirements.in` and carries every transitive package pinned and hashed. The
flag is what makes the lock a lock: without it pip will install a resolution the
file does not describe, and the hashes are decoration.

Three packages move with it:

    litellm     1.83.7  -> 1.101.0
    aiohttp     3.13.5  -> 3.14.3
    slack-bolt  1.29.0  -> 1.30.0

**aiohttp is the one that mattered, and nothing here ever chose it.** It arrives
through litellm and slack-sdk, so no version of this repo would have bumped it,
and 3.13.5 predates the 3.14 line where a batch of request-smuggling and
redirect credential-leak fixes landed. `requirements.in` now carries a floor on
it -- a floor on a package we do not import is the only way to say "not below
this" about something nobody declared.

## Changing a dependency from here

    uv pip compile --universal --generate-hashes \
        --python-version 3.12 -o requirements.txt requirements.in

`--universal` is load-bearing: the deployment is macOS and CI is linux, so a
lock resolved for one would be wrong for the other. Verified both ways -- `pip
install --require-hashes` on macOS/py3.12 and on linux/py3.12 -- before this
shipped.

## What CI does now

- Installs with `--require-hashes`, so a hand-edited lock fails loudly.
- Runs `pip-audit --strict`. Strict because without it a package the audit
  cannot resolve is *skipped*, and the gate passes having audited less than
  everything -- the wrong failure mode for a guard whose job is noticing what
  nobody is watching.
- `selfcheck` section 38 checks, offline, that every requirement in the `.in`
  is pinned in the lock and satisfies its floor, using PEP 440 comparison. No
  step re-compiles the lock against live PyPI: that would go red the moment any
  transitive package published a release, which is someone else's upload
  failing this build.

## Also

`selfcheck` now builds the LiteLLM Router for real (section 20c). Every other
section stubs `llm.complete`, so nothing in the suite would have noticed litellm
renaming a Router kwarg, moving `CustomLogger`, or changing the failure
callback's signature -- and this release jumps 17 minor versions of it. The gate
was added before the bump rather than after, and it asserts that Router still
raises on an unknown kwarg, since "does it still validate" is itself something a
version bump can change.
