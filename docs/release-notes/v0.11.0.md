One issue, and it makes a scope key that read like a gate behave like one.
`github_repos` now resolves the repo an operation *targets* rather than the
repo the current directory happens to point at -- so commands that used to pass
will start asking, and a channel whose normal work includes any of them needs
its policy widened or the work rerouted.

## What an upgrade requires

**Check your `github_repos` channels against this list (#150).**

Nothing to add or edit unless one of these is part of a channel's normal work.
Each **used to pass** with a whitelist set, and each now blocks, measured
against a channel scoped to `mine/*` in a checkout whose origin is `mine/repo`:

    gh api repos/other/secret/contents/README.md
    gh api /repos/other/secret/issues
    gh issue list --repo=other/secret
    GH_REPO=other/secret gh issue list
    gh -Rother/secret pr list
    git -C <a directory whose origin is out of scope> push

`gh api` is the one that matters. It addresses a repo **by path** rather than
by flag, it reaches read and write alike, and `gh api*` was commonly
allow-listed before #148 -- so out-of-scope and uncarded coincided exactly.

**Two refusals are new in kind, not just in coverage:**

- `gh api graphql` and `gh api user` are **refused** while a whitelist is set.
  The first names its target inside the query; the second has none. "Could not
  tell" has to mean no for the one command that reaches every repo the token
  does. A channel that uses `gh api graphql` legitimately will notice this.
- A path containing `..` -- `repos/mine/repo/../../other/secret` -- is refused
  rather than normalised. Normalising means being sure ours matches whatever
  the API does; refusing needs no such assumption.

**One thing got less strict**, and it fixes a false refusal: the comparison is
now case-insensitive. GitHub owner and repo names are, so `mine/*` refused
`MINE/REPO` -- a repo that is in scope, blocked for being spelled differently.

## What it still does not do

`github_repos` is **a textual guard, and not containment.** The README now says
so at parity with how `exclude`'s first half is already described. It reads the
command; it does not hold the credential. A repo named through a spelling not
listed above, a URL assembled at runtime, or a redirect all pass it.

There is no kernel behind this one -- the sandbox confines the filesystem,
never the network -- so what bounds the blast radius is the token's own scope.
A channel whose token can reach a repo it must not touch is a token problem
rather than a policy one.

One residue is worth naming because it is deliberate: a `gh alias` expands to
`api ...` inside gh, so the word never reaches this check, and a repo-less `gh`
command falls back to the checkout's origin. That fallback is correct --
`gh pr list` names no repo by design -- and the alias is not reachable from a
channel: the sandbox denies gh's own config, including through `gh alias set`.
An alias therefore has to have been created by the operator, which is trusted
configuration at the same tier as the policy file itself.
