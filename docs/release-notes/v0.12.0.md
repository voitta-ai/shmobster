`github_repos` now applies to commands it was silently skipping. Same key, same
policy files, nothing to edit -- but a channel that reaches another repo by any
of the spellings below will start being refused, and one of those spellings is
ordinary enough to be in daily use.

## What an upgrade requires

**Check your `github_repos` channels against this list (#186).**

Each **used to pass** with a whitelist set. Measured against a channel scoped
to `mine/*` whose checkout points at `mine/repo`:

    cd vendor && git push                    <- the ordinary one
    pushd vendor && git push
    (cd vendor && git push)
    cd vendor ; git push
    git --git-dir=<dir>/.git push
    git --work-tree=<dir> --git-dir=<dir>/.git push
    GIT_DIR=<dir>/.git git push
    GIT_WORK_TREE=<dir> git push
    /usr/bin/git -C vendor push
    ./git -C vendor push
    /opt/homebrew/bin/gh api repos/other/secret/issues

**`cd <dir> && git push` is the one to look at.** It retargets git exactly as
`git -C <dir>` does, and only the flag was being read -- so the whitelist was
one keystroke from irrelevant, and the keystroke is one people type without
thinking.

**The path-prefixed invocations are the older hole.** `_check_github` decided
whether a command was git with an exact token match, so `/usr/bin/git` was not
git at all and the check returned "nothing here" rather than checking. That
predates the retargeting work entirely; every spelling this release closes was
reachable again by putting a path in front of the binary. Matched by basename
now.

## What got less strict

Three commands that were wrongly refused now run, because the check records a
directory where git **runs** rather than everywhere the line visits:

    pushd vendor && popd && git push     git runs at home
    git -C vendor -C ../inscope push     git chains -C, so this is inscope
    (cd vendor && ls) && git push        a subshell gives the directory back

The last one was also answering *inconsistently* -- the `;` spelling of the
same command was allowed while the `&&` spelling was refused.

## #186's premise was wrong, and that is worth recording

The issue said a channel could `git init` in TMPDIR, plant a hook and commit,
reaching what #184 closed by another door. It cannot. #184's deny is a regex
and is not anchored to the channel's tree, so it already covered a repository
anywhere -- TMPDIR included. The `core.hooksPath` routes are closed too: a
channel cannot write `~/.gitconfig`, `~/.config/git/config`, or run
`git config --global`. All of it is asserted in `selfcheck.py` now rather than
believed.

TMPDIR stays a writable root. The question was never what may be *written*
there, but what may be *executed* from there.
