The agent answers direct messages now (#23). One new Slack event, no new config
key, and one thing to check on the Slack app side before it works.

## What an upgrade requires

**1. Subscribe to `message.im` in the Slack app (#23).**

The bot event subscription list needs `message.im` alongside `app_mention`. The
`im:history` scope was already in the recommended set, so this is the event
subscription rather than a new permission. Without it nothing breaks -- DMs
simply keep going unanswered, exactly as before.

**2. Decide whether DMs need their own policy.**

A DM resolves to a `D...` channel id and takes a policy like any other. A
deployment that has not named one gets `default_policy` -- so if the default is
broader than you would want in a one-to-one conversation, name the DM channel
explicitly:

    "D0123456789": { "cwd": "...", "github_repos": ["..."] }

**Trust does not change with the door.** `trusted_users` is per user, so the
same person has exactly the same authority in a DM as in a channel. Nobody
gains anything by moving the conversation; the only thing that changes is that
no mention is needed, because in a DM the message is the address.

## Why a DM is answered and a channel message is not

In a channel the mention is the address. Answering every message there would
make the agent a participant in conversations nobody asked it into. A DM has no
one else in it, so requiring `@shmobster` is a tax with nothing on the other
side of it.

A DM is otherwise the *same turn* as a mention -- one code path serves both, so
a DM cannot quietly miss what a mention gets: attachments, thread context, the
`:eyes:` ack, the Approve/Deny cards for anything the turn parks.

## One operational note

If the bot's user id cannot be resolved at startup, **DMs are refused and
mentions still work**, and the log says so:

    bot user id unresolved, so direct messages will not be answered (#23);
    mentions are unaffected. Check the bot token and auth.test

That is deliberate. An agent posts its replies into the same DM they came from,
and those replies arrive back as message events -- so an agent that cannot
recognize its own posts is one that can answer them, in a loop. Not knowing who
we are is a reason not to answer rather than a reason to skip the check.
