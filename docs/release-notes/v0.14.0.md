Two features, no new config key, and nothing an existing deployment must change
to keep working. Both are opt-in by presence: a channel with no `MEMORY.md` and
a deployment that never asks about cost see no difference.

## What an upgrade requires

Nothing mandatory. Two things worth doing.

**1. Give a channel a memory, if it wants one (#140).**

Put a `MEMORY.md` beside that channel's skills in the private catalog --
`channels/<channel>/MEMORY.md`, or inside the skills directory. It is injected
as standing context: which box runs what, who owns which alert, the name of the
thing everyone calls something else. A skill is a procedure; memory is what a
procedure assumes.

No config key. Memory rides the `skills` entries the channel already has, so a
channel without them has no memory and pays nothing.

**It is reference, and it is built so it cannot be anything else.** Three
properties, each enforced rather than asked for:

- **The agent cannot write it.** A `MEMORY.md` under any of the channel's
  writable roots is ignored with a warning -- and so is one in the catalog that
  turns out to be a *symlink into the tree*, which is the same hole wearing a
  hat. In-tree writes run without a card (#117), so either route would make one
  granted `cat > MEMORY.md` into next turn's prompt.
- **It reads as data.** The body is fenced, with a fence longer than any
  backtick run inside it so the content cannot close its own block, and the
  block says what the text cannot do: it grants nothing, and a line that reads
  like permission is stale or someone testing.
- **It never reaches a tool.** Nothing but the prompt builder imports the
  module, and `selfcheck` asserts the import graph rather than the behavior --
  that is the property that has to survive somebody later writing a tool that
  "just needs the context".

There is deliberately no tool for the agent to write its own memory. Editing it
is a pull request against the catalog.

**2. Ask what things cost (#190).**

Every model call now records vendor, model, tokens and cost into the turn's
trajectory record. In a channel:

> what did this thread cost?

`report_cost` answers for this thread and this channel today, including the
turn in flight. It takes no arguments -- the turn knows where it is.

From the host:

    scripts/costs.py                 # today, every channel
    scripts/costs.py --days 7
    scripts/costs.py --channel C123

**Unknown cost is never zero.** A subscription rung and a model missing from
LiteLLM's cost map both produce no number, and a rollup showing those as free
is wrong in the one direction nobody audits. Tokens are recorded either way,
and every total carrying one says the real figure is higher. The same rule
covers a call nobody could attribute to a configured vendor: it is named, not
folded into a bucket that reads as complete.

Turns recorded before this release carry no `calls` key and are skipped by the
rollup rather than counted as free.

Budget *enforcement* is out of scope and stays LiteLLM's job (#51).

## Note for the deployment

The live box is on **v0.8.0**. This is v0.14.0, and v0.9.0's notes are the ones
that matter most on the way up: the supported voitta-yolt range inverted there,
from `>= 1.6.0, < 2.0.0` to `>= 2.0.1`. Read `docs/release-notes/v0.9.0.md`
before upgrading, then v0.11.0 and v0.12.0 for the `github_repos` changes.

Two of the four things `docs/HANDOFF.md` says 1.0.0 waits for are that upgrade:
the deployment being on a released build, and voitta-yolt 2.0.x having run
underneath it for a couple of weeks. The second clock has not started.
