One change, in the layer that decides whether a command needs a human: a
redirect that opens no file is no longer counted as a write. Nothing to
configure, nothing to migrate. Channels get fewer approval cards for commands
that were never writing anything, and one hole closes in the same rule.

## What an upgrade requires

Nothing. No new config key -- the seventh release running.

## Fewer cards for reads that were never writes (#213)

`2>&1` opens nothing. It points one descriptor at another, and `2>&-` closes
one; neither names a path, so neither can write. The grant layer allowed `<` as
its only non-writing redirect and failed closed on everything else, which is the
right default and the wrong answer here: both counted as writes, and a write
shadows the read rule.

So this parked for a human:

    jq '.. | objects | select(.id? == "8332:23593")' structure.json 2>&1 | head -c 6000

A local read of a file already on disk, no network, and the agent said so on the
card. The gate disagreed for a reason that had nothing to do with what the
command does, and the card blamed the verb (see below).

Measured in a live channel before the fix: of nine approval cards in one thread,
**three were local `jq` reads parked only because each ended `2>&1 | head`**.

### Why it is safe to relax

bash spells a descriptor duplication and a two-stream file write with the same
operator. `>&2` writes nothing; `>&out.txt` creates a file.

This does not re-implement that rule. tree-sitter has already applied it and
types the two destinations `number` and `word`, so the check reads the parse
rather than pattern-matching the string. Anything that is neither -- an
expansion, an unrecognized destination -- stays on the write path, and `&>file`
with it.

Unchanged, and asserted:

| still needs a card | why |
|---|---|
| `cat f >&out.txt` | `>&` with a `word` is a file |
| `cat f &>out.txt` | `&>` is a file |
| `cat f >&$X` | an expansion is not a literal |
| `cat f 2>&1 > out.txt` | the `>` still writes |
| `curl ... 2>&1`, `rm -rf / 2>&1` | a dup does not launder the verb |

An adversarial review argued `>&01`, `>&08` and `>&999` might be typed `word`
and let a file through. Measured: all three type as `number`, and bash answers
them as descriptors -- `>&08` exits 1 with `8: Bad file descriptor` and creates
nothing.

## A write that got in by word order (#213)

Found while reviewing the above; it predates it, so it was live in every release
that had the grant layer.

    >out.txt cat f     was granted as "cat: read-only"  -- and wrote out.txt
    cat f >out.txt     parked for a card

Same command, same effect, opposite verdict, because only the trailing form
parses as a `redirected_statement`. A leading redirect is a child of the command
node, which the redirect check never saw and `argv()` skipped outright.

The per-redirect judgment now lives in one function that both parse shapes call.
A rule only one of two spellings reaches is decoration.

The sandbox already confined such a write to the channel's tree, so this was
never a route out of the box -- but "does this need a human" was being answered
by word order, which is not an answer.

## The card said the wrong thing

A read verb refused for its redirect used to produce `no rule: jq` -- the
classifier's words about its own ruleset, surfaced as though the verb were the
problem. `jq` has been in the granted read set the whole time, so anyone
debugging that card went to check a list that already had the verb in it.

It now says the segment redirects output to a file, which is the actual reason.

## Checks

`selfcheck.py` check 48: 7 duplication forms must grant, 6 leading-redirect
writes and 8 trailing ones must not, 2 mutating verbs must not be laundered by a
dup, the two spellings of one write must agree, and the refusal must name the
redirect rather than say "no rule".
