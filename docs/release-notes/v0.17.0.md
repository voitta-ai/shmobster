One change, in the approval surface: a refused click now carries the Approve /
Deny buttons instead of pointing at them. Nothing to configure.

## What an upgrade requires

Nothing. No new config key -- the eighth release running.

## "The card above" was true and unusable (#215)

When someone who is not a trusted user clicks Approve or Deny, the card is left
standing on purpose -- refusing a click must not consume the request -- and the
alert said so:

    :warning: @someone clicked Approve on request [...], but only trusted users
    may act on a parked command -- nothing ran. The request is still parked and
    the Approve / Deny buttons on the card above are still live, so @trusted can
    act on it there.

Every word of that is accurate. It is also useless, because "above" is however
far the conversation has travelled since the card was posted. Measured in a live
thread:

    16:25:33  two cards posted, buttons live
    16:25:37  "actually I want to see @someone if you can approve"
    17:08:53  they click Approve            <- 43 minutes later
              "...the buttons on the card above are still live"
    17:09:07  "she can't :disappointed:"
    17:11:00  "what requests do I approve?"  <- had to ask
    17:11:58  "approve both"                 <- approved by typing

Both cards were checked afterwards. Still `blocks=['section','actions']`, both
buttons present, `edited` false. Nothing had expired or been consumed. The
button path was abandoned anyway, because nobody could find the buttons.

So the alert brings its own. The click lands where the conversation is.

### What that does and does not change

- **Same request id in the button.** The new card is a second door onto one
  queue entry, not a second entry. Whichever is clicked gets rewritten to the
  claimed state; a later click on the other reads "no longer pending", which is
  true, and is what the card lifecycle has always done (#109).
- **Only a genuinely pending request gets one.** Held means another surface is
  already acting; absent means it cannot be acted on. A card in either is a
  button that does nothing -- the same failure with the sign flipped.
- **The command is rendered once.** The card shows it, scrubbed. Printing it in
  the alert text as well would be two chances past the scrubber (#72).
- **No new way to flood a channel.** One alert per user per request already
  bounded this and still does: six clicks from one stranger post one message;
  three strangers post three. Identical to the text version, because the bound
  was never on the content.
- **A long command keeps the alert and loses the card.** Slack refuses a section
  over 3000 characters, and a parked command can be longer. Forcing a card there
  would make the post fail, and a failed post means the trusted users are never
  told the click happened -- the one thing this path owes them. Such a command
  has no original card either, so the alert falls back to the old wording, which
  was always text and always fit.

## Checks

`selfcheck.py` check 49: the alert carries both buttons bound to the same id;
the explanation survives as a block, since blocks win over `text` in the client;
the command renders exactly once and reaches the card scrubbed; held, absent and
oversized carry no buttons at all; and repeat clicks post nothing.
