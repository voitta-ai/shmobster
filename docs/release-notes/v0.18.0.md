## A read that parked because one flag *could* have made it a write (#219)

`READ_VERBS` is consulted on the verb alone, so its bar has always been that **no
flag can turn the command into a write**. That is the right bar for a verb-only
list, and it is why `find` and `sort` were not in it -- `find -delete` and
`sort -o` really do write.

It is also why this needed a human, measured in a live channel:

    cd <repo> && git log --oneline -5 && echo --- \
      && find . -maxdepth 2 -not -path './.git*' | sort

    the command as sent    PARK   find: rules punt
    without find and sort  GRANT  cd; git log: read-only; echo: read-only

A repo inventory. `git log` and `echo` were already granted; `find` and `sort`
were the entire card.

### The bar can move for these two

The grant layer is not verb-only any more. It parses argv and already refuses on
flags -- `git -c`, `gh api`, the `aws` value-flags. So there is now a second tier
whose members are reads **unless** a named flag appears:

| verb | refuses |
|---|---|
| `find` | `-delete`, `-exec`, `-execdir`, `-ok`, `-okdir`, `-fprint`, `-fprint0`, `-fprintf`, `-fls` |
| `sort` | `-o` in every spelling: `-o out`, `-oout.txt`, bundled `-uo out`, `--output`, `--output=` |

The bundled and attached `sort` forms are the substance, not a detail. Only
`-o out` is caught by comparing against `"-o"`, and all three write:

    sort -ro out.txt f   creates out.txt
    sort -uo out.txt f   creates out.txt
    sort -or f           tries to write a file named `r`

In a short-option cluster every character is an option letter and sort's `o`
always consumes a filename, so any single-dash cluster containing an `o` is
refused. That is exact, not conservative: `-rn`, `-ru`, `-k1,1`, `-t, -k2` all
still run without a card.

**An argument the layer cannot read is a refusal, not a guess.** `find . $F` with
`F=-delete` is a deletion a deny list cannot see.

### On the shape of the risk

This is a deny list, so a writing flag nobody enumerated would pass. Plainly:

- A flag that writes a **file** is survivable -- the sandbox confines it to the
  channel's tree, the same risk already accepted for every verb in `FS_VERBS`,
  `tee out.txt` included.
- A flag that **runs** something is not, because execution escapes the
  read/write framing entirely. So find's four execution primaries are the
  entries to be sure of, and they are the complete set in both BSD and GNU find.

### Why this does not lean on the classifier

The shortcut would be to trust voitta-yolt's `find: rules punt`, which reads like
a verified negative -- its `check_unsafe_flags` runs before the default dispatch,
so it means "I have a rule, I checked its unsafe flags, none matched", which is
genuinely different from `no rule: sort`. It does not hold where it matters:

    find . -maxdepth 1                    ('unknown', 'find: rules punt')
    find . -name x -fprint /tmp/out.txt   ('unknown', 'find: rules punt')
    find . -name x -delete                ('unsafe',  'find: flag -delete (no value)')

The first and second are byte-identical and the second writes a file. The
omission is deliberate upstream, for a reason about its own internals. Reported
there as a measurement, along with two more instances of the same gap; this list
stands either way and becomes defence in depth if the rule closes.

`uniq`, `awk` and `xargs` stay out, each for its own reason: uniq's output
destination is a bare trailing positional that no flag check can filter, awk's
`system()` is not a flag, and xargs runs its argument.
