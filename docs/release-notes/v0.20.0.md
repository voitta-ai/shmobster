The learning loop's first real run produced two issues, and this is both of
them: the self-check that skipped the most skill-worthy turn in a thread, and
the destination that put a generic skill somewhere only one channel could see.

## What an upgrade requires

Nothing mandatory. **One new config key, optional and defaulted** -- the first
in eleven releases, and it needs no action unless you want a different shared
destination.

    "learning": { "shared_path": "shared/skills/{name}/SKILL.md" }

Also worth doing on any machine that pushes to this repo:

    git config core.hooksPath scripts/hooks

## The bar names the shape the self-check missed (#211)

First real run: the agent's earlier answer in the thread was wrong, a trusted
user supplied three counter-facts, it re-derived the right mechanism and stated
it as a general rule -- and did not flag. The card came a turn later, only once
a trusted user asked whether the thread had met the bar.

Settled from the code. Of the issue's three hypotheses the "already considered"
one is **wrong** -- `mark_thread` fires only on flag, propose or decline, so
nothing had marked that thread. The bar's shapes are the right hypothesis, and
the cause under it is structural:

**The feature promises an end-of-turn self-check and there is no such thing.**
`flag_skill` is a tool called during composition, so a judgment about the turn's
*conclusion* is being asked for through a mechanism that runs before the
conclusion exists.

This does not invent the missing hook. It stops the bar describing the wrong
subject:

- **The correction shape is named, as the strongest one.** The old text listed
  three shapes and every one was something you *do*. The turn it missed was one
  where the agent mostly read three facts and thought. "Your earlier answer in
  this thread was wrong and you now know why" is now listed first among equals,
  because the thread then holds both the wrong belief and the evidence that
  corrected it -- exactly what the next person needs. And it says not to skip it
  because the correcting facts came from a user: what is worth writing down is
  the rule, not who supplied the input.
- **Judge the conclusion, not the tool calls.** Both directions: a turn that ran
  no commands and reasoned its way to a general rule can meet the bar; a turn
  that ran ten and answered a routine question does not.
- **Answer "why no card" instead of flagging.** The run ended with the agent
  flagging when asked and not answering the question. A card produced on request
  is a card on demand, which #129 says it must not be.
- **The bar is in the system prompt**, not only the tool description -- in view
  while the answer is composed, rather than once the model is already deciding
  to call something. One string, both readers.

### The trajectory says whether a turn could have flagged and did not

    "flag_skill": "used" | "offered, not used" | "not offered"

Read with the step count the record already carries. Deliberately **not** the
model's reason for declining: capturing that means asking every turn and paying
a model call to hear "no" almost always.

A self-check that silently never fires and one that fires and declines produce
the same empty thread. That is why this miss had to be caught by a human asking
in channel, and it is now greppable instead.

## Scope is a property of the skill, not of where it was learned (#210)

The same run landed a generic GitHub mechanism -- a ruleset's required context
from a workflow added after the PR's last push never runs, nothing in it about
the channel, the company or any private host -- under `channels/<ch>/skills/`.
Only that channel would ever see it, a second channel would learn it again, and
the private catalog fills with things that are not private.

#130 chose per-channel storage to solve #52's envelope leak. Right for a skill
that **is** channel-scoped; wrong as the *default* for one whose content is
generic.

The card now shows the proposed scope **and its reasoning**, because a proposal
you cannot check is one you have to take on faith:

    :bulb: Worth a skill? [k-1] `github-ruleset-required-check` -- ...
    scope: every channel -- nothing channel-specific found in the name or reason
    if this belongs in the public catalog, hand it to the skillz session --
    this instance does not publish there
    To change the scope, say so when you approve.

The classifier is crude on purpose and **biased towards `channel`**. A private
skill in the private catalog costs a re-learn; a channel-specific one proposed as
shared is the envelope leak. "Could not tell" resolves to the narrower answer.

**The draft is re-checked, not just the flag.** The scope was decided from a
one-line summary while the file that lands is the draft -- a generic name can sit
on a body full of this channel's hostnames. When the two disagree in the unsafe
direction the proposal is re-parked under the same id rather than resolved either
way: choosing silently would either ship a channel-scoped skill everywhere, or
overrule a trusted user who asked for `shared`.

**Dedupe.** An existing skill covering the same ground is named on the card and
in the PR body as an amend target, instead of a sibling being drafted beside it.

**No public button.** Publishing needs the catalog.json, bundle-symlink and
version-bump wiring that claudeception owns, and a second copy here would drift.
A shared card names the handoff rather than offering what this instance cannot
do.

**Override in words.** `propose_skill` takes an optional `scope`; a trusted user
says "open it for every channel". No new button, so the click path approvals and
proposals share does not grow a third action. An unrecognised value is ignored
rather than guessed at.

## A client name reached this public repo (#227)

`docs/handoff/2026-09-17.md` carried an organisation name inside a session
transcript path, merged in #212. CI passed it and would again:
`check-sensitive-terms.sh` has two halves and a public runner can only run one --
the name wordlist is per-machine and deliberately in no repo.

#204 made the script say which half ran. This is that gap landing something.

Fixed forward; no history rewrite, because a rewrite does not unpublish -- the
commit stays fetchable by SHA and the PR diff stays rendered.

`scripts/hooks/pre-push` now runs the same script over the same paths before a
push, on the machine where the wordlist actually lives. Positive-controlled: it
exits 1 on the pre-fix file and 0 on the fixed one.
