One change: a command that failed no longer reaches the model looking like one
that worked.

## What an upgrade requires

Nothing. No new config key.

## A failed command read exactly like a successful one (#233)

`run_shell` named the exit status **only when there was no output at all**:

    retval = out.strip() or f"(exit {proc.returncode}, no output)"

So a command that failed *and* printed something said nothing about having
failed. The status existed -- on the log line one above it, which is the one
reader that does not need it.

Measured live on v0.20.0. `gh` has no credential inside the sandbox, so this
exited non-zero:

    gh api repos/<owner>/<repo>/contents/.github/workflows --jq '.[].name'

and this is everything the model received after the approval click:

    APPROVED by <@user> and ran: gh api repos/<owner>/<repo>/contents/...
    To get started with GitHub CLI, please run:  gh auth login
    Alternatively, populate the GH_TOKEN environment variable with a GitHub
    API authentication token.

No status anywhere. It reads as output, and `gh`'s banner is the only tell that
it is a refusal to run rather than a finding. The turn treated it as findings.

### What changes

    echo hi                     'hi'                           ran
    sh -c 'echo out; exit 3'    'FAILED (exit 3)\nout'         failed
    sh -c 'exit 4'              'FAILED (exit 4), no output'   failed
    sh -c 'echo fine; exit 0'   'fine'                         ran

The status goes **first** -- it is the thing most likely to change how the rest
is read, and everything downstream that classifies a result looks at the head.
**Success is untouched**: no marker, no new noise in front of the output.

### The trajectory can tell "could not run" from "ran and said no"

A non-zero exit now records `failed` rather than `ran`. `error` keeps its
meaning -- the command never started, a timeout or a sandbox that would not wrap
-- so the two are finally distinguishable, which one `ran` bucket made
impossible.

### A resumed turn is told which it was

"It ran" used to be all the model got, whatever the command exited with. That is
how a turn ends up reporting what a command *found* when the command was
declining to run at all. It now reads:

> it ran and FAILED -- treat its output as a failure report, not as findings

### Two things deliberately not done

**No matching on `gh`'s "To get started with GitHub CLI" string.** That is one
vendor's spelling of a status the process already returned.

**No machine-readable status header.** An adversarial review proposed framing the
status as `\x1e`-delimited JSON. The detection is a substring, and a substring can
collide -- a successful command that prints `FAILED (exit 9)` in its own output
will be recorded as failed. That asymmetry is the point: a **failing** command can
never read as successful, because the marker is prepended rather than matched for.
A spurious failure claim is visible in the next line and costs a re-read. A missed
failure is the bug this release fixes. Machine framing in text a human reads on a
Slack card is the worse trade.

## Checks

`selfcheck.py` check 54, including the one review finding that would have been a
real defect: truncation cannot eat the marker, because the output is capped
first and the status prepended after. Verified at 20 KB of output, through the
trajectory's own result cap, and through the wrapped form the resume path sees.
