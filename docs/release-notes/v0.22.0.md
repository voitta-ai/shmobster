One change: shmobster now says at startup when its own config holds credentials
at rest.

## What an upgrade requires

Nothing. No new config key. One new **optional** environment variable,
`SHMOBSTER_REQUIRE_ENV_SECRETS=1`, which turns the new warning into a refusal
to start.

**You will probably see a new warning on first boot.** That is the point.

## A sentence is a test nobody wrote (#231)

`CLAUDE.md` has said since #73 that config values are `${VAR}` references,
*"including in a running deployment's own `shmobster-config.json`, not just the
example"*.

The development box holds **five** literal credentials -- both Slack tokens and
three waterfall `api_key`s. Two full-machine credential sweeps ran past them:
`scrub.py --apply` rewrote 1014 spans across 52 files on 2026-09-17 and never
touched that file, because the sweep's roots never covered shmobster's own
surfaces.

Startup now says so:

    config: config holds literal credentials where #73 requires ${VAR}
    references: /slack/bot_token, /slack/app_token, /waterfall[0]/api_key,
    /waterfall[1]/api_key, /waterfall[2]/api_key -- move the values into the
    environment (launchctl setenv / the plist's EnvironmentVariables on macOS)
    and replace each with ${VAR}

...and separately, if the file is readable past its owner:

    config: shmobster-config.json is mode 0644; it is readable beyond its
    owner. chmod 600 it

### Why the check reads the raw config

This is the load-bearing detail, and the reason a simpler version would not
work at all. After `_interpolate`, a `${VAR}` reference **has already become**
the value it referenced -- so at that point a correctly configured deployment
and a badly configured one are byte-identical. The check therefore runs on the
config as parsed from disk, before expansion. Both directions are asserted.

### Two deliberate narrowings

**Matched on the key, not the value.** A key named `bot_token` holds a
credential whatever is in it, and inferring from the value means maintaining a
list of every vendor's prefix that goes stale the first time one changes.

**Paths are reported, never values.** The complaint is a file that should not
hold secrets; quoting one into a log would be the same mistake one layer along.

### Warn, not refuse -- and why, given the week this repo has had

`SHMOBSTER_REQUIRE_ENV_SECRETS=1` makes it fatal. It is not the default.

That sits oddly next to #204 and #229, both about gates that pass while
switched off, so the distinction is worth stating: **enforcement is right when
stopping removes the risk.** Here it does not. Refusing to start bricks a box on
upgrade over a condition that predates the upgrade, and a stopped agent does not
remove the token from the file -- it removes the operator's chance to read the
warning. Where a gate's passing is the risk, enforce; where the gate is only a
notice, a refusal buys nothing but downtime.

### What to actually do about it

Move each value into the environment and replace it with `${VAR}`. On macOS the
process is launchd-run, and **launchd does not read `~/.bash_profile`** -- use
`launchctl setenv` (osx-env-sync) or the plist's `EnvironmentVariables`.

Worth doing while a token is being reissued anyway: the value has to be replaced
either way, and putting it in the right place costs nothing extra at that moment.

Stated plainly rather than oversold: this moves which surface exposes the secret,
it does not make it secret. `launchctl getenv` is readable by the same user. What
it buys is one place to rotate, consistency with the rule the repo already has,
and removal of the copy sitting in a working tree.

## Checks

`selfcheck.py` check 55, including the proof that the interpolated form is
indistinguishable from a literal -- which is why the raw config is the input.

The fixtures there are deliberately not token-shaped. The check is about a value
that is not a `${VAR}` reference and nothing about its shape, and a realistic one
trips this repo's own sensitive-term gate. It did, on the first draft, for the
second time in this repo's test data.
