Five changes from one afternoon in one live channel, where a design-file lookup
and a repo inventory took eleven approval cards between them. Four are cards
that should never have existed; the fifth is a reply that said the wrong thing
at the end of a long turn.

## What an upgrade requires

Nothing. No new config key -- the twelfth release running.

**Channels get noticeably fewer cards.** Nothing that could write gained a
grant; every change below names what it still refuses.

## A channel could hold a credential and not be able to use it (#239)

A channel with `api.example.com` in `allow_domains` and the token for it in
`env` still parked every `curl`. This layer had no rule for fetch verbs, and
voitta-yolt 2.0.x answers `unknown` for them, so each one was delegated to a
layer that could not vouch for it. The tool that does honour `allow_domains` --
`web_fetch` -- sends no headers, so the authenticated read had no uncarded path
at all, and a design review cost one approval per lookup.

Reach did not move. `check_egress` is the same function with the same answers:
a host that is not statically visible, a host outside the list, and the
upload-shaped flags #222 added are all still refusals. What moved is that
meeting those conditions is now a grant rather than a punt.

Three narrowings, each deliberate:

- `wget` is not included: it writes the response to a file by default.
- A fetch that writes the response to a file still parks -- `-o`, `-O`, `-J`,
  `--output-dir`, and clusters containing those letters. Content from off the
  box landing in the tree under a name the command chose can have its own card.
  `-o /dev/null` is the exception, because the three devices are not files
  (the same exception the redirect rule already makes), so a status-code probe
  runs.
- Reach is checked before shape, because `-sXPOST` carries an `O` inside its
  attached value and a cluster scan cannot tell that from `-sO`.

The argument rule is what makes the credential case work: a quoted word whose
first character is a literal non-dash cannot become an option, whatever it
expands to. So `-H "X-Api-Key: $TOKEN"` is granted while `"$OPTS"`, unquoted
`X-Token:$T` and `"-d@/etc/passwd"` are not.

## Six commands that only read no longer need a human (#236)

`git branch -a`, `git for-each-ref`, `git remote -v`, `git worktree list` and
`gh auth status` parked while `git log`, `git status`, `ls` and `gh pr list`
ran with no card. A combined read parks if any one component does, so a repo
inventory cost four clicks for the one verb in it that was missing.

`for-each-ref` has no writing form and joins the read list outright. The others
are decided by what follows them:

| command | still parks on |
|---|---|
| `git branch` | any flag outside the listing set, and any bare word -- `git branch <name>` creates |
| `git remote` | anything but `-v`: `add`, `remove`, `rename`, `set-url`, `prune` write, `show` and `update` contact the remote |
| `git worktree` | anything but `list`: `add`, `remove`, `move`, `prune`, `repair`, `lock` |
| `gh auth` | anything but `status`, and `--show-token` in every spelling |

`git branch` is an allowlist rather than a deny list, the opposite choice from
`find` and `sort`, and the reason is worth stating: those write a file the
sandbox still confines, while `branch` destroys repository state the sandbox
has no opinion about. An unlisted flag parks.

**Two holes the adversarial review found before this shipped**, both
reproduced against the installed tools rather than argued from the code:

- `gh auth status --show-token=true` printed the credential. gh's flags are
  cobra booleans, so the `=` form is the same request, and an exact-token check
  did not recognise it.
- `git branch --color newtopic` created a branch. `--color`, `--column` and
  `--abbrev` are documented `[=<value>]` and do not consume the next word, so
  treating it as their value handed a listing grant a branch creation. Verified
  in a scratch repo: `--color newtopic` left `newtopic` behind, `--abbrev 7`
  left `7`. Hence the no-bare-words rule above, which costs the detached
  `--sort committerdate` spelling and closes the class.

## An approved command that failed said so, and the record did not (#233)

#234 gave every path the exit status. The one it left was the approval path:
`run_approved` returns `APPROVED by <@u> and ran: <cmd>\n<out>`, so the marker
sits after the approval line, where a head-only check cannot see it. The
trajectory recorded `approved` for a deploy that did not happen -- and the
commands reaching that path are the ones a human was asked about. It now
records `approved-failed`.

The false positive `failed()` documents comes along: a successful
`grep "FAILED (exit " app.log` reads as failed, because the wrapper quotes the
command too. Asserted rather than fixed, for the reason `failed()` already
gives -- a wrong "failed" is contradicted by the next line, a missed failure is
what the record exists to carry.

## A turn that hit the step cap now says so (#251)

At the cap the loop has stopped calling tools and asked the model to answer from
what it had, so the reply is an interim report. It carried the same note as a
turn that merely came close: "used 50/50 tool steps (nearing the limit --
consider narrowing the request)". That reads as a healthy turn with a footnote.

Seen live: the answer above that note ended "now let's add the Dashboard,
Review Answers and Share Card screens" -- a plan, not a result -- with nothing
saying the work had been cut off or that asking for the rest was the next move.
It now says it stopped at the limit, that the answer is what it had, and that
asking it to continue will pick up from there.

The cap itself is unchanged and stays configurable (`max_tool_steps`,
`warn_tool_steps`). The review's catch here was worth more than the change: the
state is passed, not inferred from the step count, because a turn that answers
on the last allowed iteration also reaches the cap -- having finished.

## What is still carded, and known

- `gh api`, including a plain GET to a repo the channel's `github_repos`
  already names. That is the largest remaining source of cards in a channel
  doing GitHub work, and it is #150's open scope question.
- `git ls-remote origin`: the host is not statically visible, so the egress
  check cannot see where it goes.
- Any fetch writing to a real path, any `git`/`gh` subcommand that writes, and
  every command outside the read set. Unchanged, on purpose.
