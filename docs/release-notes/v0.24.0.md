Two changes, both about the same complaint: a channel set up to work on one
repo spent its day asking permission, and when it did ask, nobody could act on
the question without reading the thread back.

## What an upgrade requires

Nothing mandatory. **One new config key, opt-in and off by default** -- the
first since v0.20.0.

    "unattended": true        // in a channel's policy, policy file only

Nothing changes for a channel that does not set it.

## The channel's scope is the boundary, not the command's shape (#253)

A card was being paid per mutating command even when the command was squarely
inside what the channel exists to do. Measured in one thread: eleven approvals,
every one a `git` or `gh` operation against the single repo that channel works
on.

In an **unattended** channel, `git`, `gh` and the file verbs run with no card,
destructive ones included -- `rm -rf`, `git push --force`, `gh pr merge`,
`gh api -X POST`. The people in such a channel are being enabled rather than
supervised, and a mess in their own workspace is theirs to make.

Three boundaries do not move, because each one leaves that workspace:

- **`github_repos` still says which repo.** Since #193 that is the operation's
  target, not the directory's origin, so `gh api repos/<other>/<secret>` is
  blocked in an unattended channel exactly as it is anywhere else.
- **`allow_domains` still says which hosts.** A `git push` to an unlisted
  remote parks like any other fetch.
- **The sandbox still says which tree**, and this deployment's own config stays
  unreachable.

**Interpreters are deliberately excluded** -- `sh`, `bash`, `python3`, `node`,
`perl`, `ruby` -- although they cannot escape the tree. The sandbox confines the
filesystem and not the network, so `python3 -c` with a socket would be an
uncarded fetch to anywhere, and `allow_domains` would be decorative.

voitta-yolt's `deny` verdict also stops short-circuiting in such a channel. Its
2.0.x predicates are about the state of the repository the channel works in,
which is the "you might make a mess of your own workspace" case this mode
exists to stop asking about.

### What the adversarial review caught, before this shipped

The first implementation granted `git` and `gh` **on the verb**, which skipped
the parsing that refuses a command-bearing option. Measured against real git,
both of these execute through a shell:

    git -c alias.pwn='!echo ...' pwn          -> runs
    git config alias.pwn2 '!echo ...'; git pwn2 -> runs

Either is an arbitrary command with no repo and no host in it for either
allowlist to read. So unattended no longer touches the verb dispatch for those
two: it changes the verdict their own handlers reach, after the `-c` refusal,
and only for a subcommand git or gh actually defines. An unknown word is an
alias, and an alias is somebody else's command. `git config` is excluded for
the same reason it exists (`core.fsmonitor` runs a command on the next ordinary
read), as are `gh extension`, `gh alias`, `gh codespace` and `gh auth`.
`gh --hostname` is refused: another GitHub host is another namespace, and
`github_repos` describes one.

Fixing that turned up a second thing, in the other direction: `git push` names
no host, so the textual egress check had nothing to read and parked the
commonest command such a channel runs. It now resolves the named remote's
configured URL -- where the bytes actually go -- and checks that host. A remote
that does not resolve is a refusal, not a pass.

### Visibility

A channel that never parks anything looks exactly like a quiet one, so:

- every boot logs which channels are unattended, by name, with their repos and
  their tree;
- `describe_capabilities` says so in that channel, in as many words, including
  what still parks.

The key is policy-file only, like `env_passthrough`: a channel must not be able
to talk itself into this.

## A parked command answers both of its readers (#256)

One reply used to serve neither. The person who asked got a command line, a
reason in the gate's vocabulary, and a request id they cannot act on -- they
had asked for an outcome. The trusted user who *can* act got no more than that,
so approving meant scrolling back to work out what the command was for.

The reply now carries both halves, in the order the readers need them: a
one-line `tl;dr:` for the asker with no command, no flags and no id, then
`for the approver:` with the exact command, what it changes, why it parked and
the id to quote. Both are tagged by id, because a request nobody is named on is
a request nobody owns.

The asker's id is rendered into the instruction rather than left to the model
-- the review's catch, and a real one: `run_shell` never received it, and the
thread transcript excludes the current message, so on a root message the model
had nothing to tag and the old self-check could not have noticed.
