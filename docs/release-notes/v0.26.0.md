One change: a channel can declare a check, and a `git commit` grant is narrowed
by whether that check passed. Opt-in per channel; a channel that declares
nothing is exactly as gated as before.

## What an upgrade requires

Nothing. One new **optional** per-channel policy key, `check_command`.

## The three commit predicates all asked the same kind of question (#238)

`linked_worktree`, `non_default_branch`, `solo_author` — every one of them asks
**how bad is it if this commit is wrong**. Is this branch work, is it yours, is
it reflog-recoverable. None asks **is it wrong**.

    "check_command": "make check"

With that set, `git commit` is granted only if the channel's check passed in
this thread. Without it, nothing changes.

    git commit: linked worktree on welcome-flow, solo author,
                check passed since last write: make check

## The gate reads a witness; it runs nothing

This is the part worth understanding, because the obvious design is the other
one.

#238 proposed that the gate run the project's check itself. That means
executing unapproved code, with side effects, **inside the decision layer** —
the one layer that has never had one, and the reason the existing three
predicates are 3-second read-only `git` calls.

So it is inverted. The agent runs the check as an ordinary command, through
YOLT, the egress list, the grant layer, the sandbox, and an approval card if
any of those asks for one. The gate then reads that this thread's record holds
a passing run.

**The agent cannot fabricate a passing record, because producing one means
going through every gate there is.** The trustworthiness is inherited from the
gate chain, not from what the check means.

## Named for what it witnesses

`check passed since last write` — not `laws_hold`, which is what the issue
proposed. What the record witnesses is narrow: *a command the operator named
ran in this thread, exited zero, and nothing has run since.* **Not that the
code is correct.**

A name that promises more than the mechanism delivers is the defect these notes
have described three times this month in verdict strings. voitta:yolt made the
point and it was the right one.

## Staleness, handled without inheriting a known hole

The natural patch is "the check must come after the last write". That inherits
the open holes in write detection — voitta-yolt#157's protected-write coverage,
and `curl -K`, whose options come from a file and never appear in argv at all —
where an undetected write leaves a witness that is **stale rather than false**,
granting where it should card.

So instead: the check must be the **last shell command that ran**. No write
detection, so it cannot be wrong that way. It costs strictness — anything
between the check and the commit invalidates the witness — and suits the
natural order: edit, stage, check, commit.

## It can only narrow

Blast radius and correctness are orthogonal, so a passing check never buys a
commit on the default branch. Asserted across the whole matrix: a conjunct
never turns a refusal into a grant.

Two limits, both found by adversarial review, both on the safe side of that
line and both written down rather than left to be discovered:

- **The witness is not bound to the repository being committed.** A check in
  one tree, a `cd`, a commit in another, and it is accepted. Bounded by #116,
  which confines a channel to its own tree, so "another tree" means another
  worktree of the same project. Worth fixing when a channel actually runs two
  projects; dead weight before that.
- **A check that needed an approval card does not register**, so it witnesses
  nothing and the commit takes a card. That costs a click, not a guarantee.

Neither can widen a grant. The worst case of both is a tightening that does not
tighten, which is where the feature started.

## The string is shown, not policed

The operator defines what "checked" means for a channel, and this layer cannot
judge the string — `check_command: "true"` tightens nothing. Policing the value
would be dishonest about which of us knows the project. Printing it is not, so
the log reads `check passed since last write: true` and a human can see the
conjunct is vacuous.

## No Bend

#238 proposed this for Bend's `bend PROOF.bend`. There is no `bend` on PATH, no
`~/.bend`, no `LAWS.bend` in any tree here, and #116 denies `~/.bend` in every
channel — a predicate that could not execute, for a tree nobody has. Bend is one
possible value of `check_command` and is special-cased nowhere, which is the
correct amount of Bend. Agreed with voitta:yolt before any code was written; the
theory side is voitta-yolt#159.

## Checks

`selfcheck.py` check 58: the witness holds only as the last command that ran; a
later command invalidates it; a check that ran and failed is not a witness; the
conjunct cannot rescue a default-branch commit; a channel with no
`check_command` is byte-identical to before; the command string reaches the
grounds; no thread means not satisfied rather than satisfied by default; and
**unattended mode (#253) does not bypass it** — the two landed in parallel and
meet in this path, so the orthogonality is asserted rather than assumed.
