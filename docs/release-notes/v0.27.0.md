Two fixes from watching a live `unattended` channel park eight approval cards
in eight minutes: a turn that could resume while a card was still waiting, and
cards that named the wrong reason.

## What an upgrade requires

**Read this one before upgrading. A box can refuse to start.**

### The agent now refuses to boot on a classifier below the floor (#229)

Until v0.26.0, a voitta-yolt older than 2.0.1 -- or none configured at all --
logged a warning and the agent served anyway. From v0.27.0 it exits.

Three consequences, in the order they will reach you:

1. **yolt-first is mandatory for the live-box upgrade, not advisory.** The live
   deployment is on v0.8.0 (#203). If its classifier is old, taking shmobster
   past v0.26.0 will refuse to start until voitta-yolt moves first. That is the
   intended order and always was; it is now enforced rather than suggested, and
   it is not a thing to discover halfway through an upgrade.
2. **Check `ThrottleInterval` in your plist.** A refused boot exits, launchd
   restarts it, and the refusal repeats. `deploy/ai.shmobster.plist.sample`
   sets `ThrottleInterval` to 10 and explains why -- an unthrottled respawn
   every ~1.7s once bloated a log to 1.8 GB. A plist that predates that guard
   should gain it *before* taking this release.
3. **Two documents said this already happened, and were wrong.** `yolt_gate`'s
   own docstring and `docs/release-notes/v0.9.0.md` both claimed "startup
   enforces this rather than trusting a pin". It did not. Both are corrected,
   v0.9.0 with an in-place note for anyone upgrading from before v0.27.0.

Why enforce here, having shipped #230 and #231 this month as warnings:
**enforcement is right when stopping removes the risk.** A classifier below the
floor answers `safe` for commands this design assumes it would not, and `safe`
short-circuits to execution before the grant layer is consulted (#222) -- a
stopped agent runs none of them. A stopped agent does not unwrite a token
(#231) or shrink a log (#230), which is why those stayed warnings and this one
does not.

Otherwise: no new config key.

## A card parked after the surfacing pass was not counted (#266)

A turn that parks several commands must resume **once**, on the last
resolution. There was a window where it did not.

`approvals.add()` did not record the thread; `claim_unsurfaced()` wrote it when
the ingest rendered the card, on the argument that the queue is
ingest-agnostic and the tool loop had no thread to give. So a request parked
*after* a surfacing pass had no thread yet, was invisible to `pending_in()`,
and the turn continued while that card was still waiting:

    before:  A surfaced, B parked but not yet surfaced
             pending_in("C1","1.1")  -> 1        two are parked
             A resolved: begin_resume -> True    resumes while B waits

    after:   pending_in("C1","1.1")  -> 2
             A resolved: begin_resume -> False
             B resolved: begin_resume -> True

Reachable exactly where it was seen: a busy thread where a resumed turn parks
its next command before the surfacing pass runs, so parks and resolutions
interleave. The tool loop has known its thread since #238, so the reason for
deferring was already gone.

`claim_unsurfaced` still fills in when no thread was given, and **no longer
overwrites** — a card surfaced into a different thread than it was parked in
would silently move which thread waits on it, so that now warns and keeps the
parked one.

A card with **no** thread at all now counts against every thread in its
channel. That cannot happen from the Slack ingest, where `thread_ts` is
`event["thread_ts"] or event["ts"]` and every message has a `ts` — but a future
ingest (#25's email) that forgot to pass one would otherwise park something
invisible. Over-strict and visible beats invisible.

### The wait is said, not logged

Two silences looked alike, and both went to a file:

    resume: [<id>] resolved, but this thread is not ready to continue
            (still parked, or already resuming)

Meanwhile the thread showed a command running and then nothing, which reads as
a task that died — and cost a human re-mention every time. Only one of those is
worth breaking silence for:

> :hourglass: [id] is resolved, and this task is waiting on 2 more requests in
> this thread. It continues on its own once the last one is approved or denied
> -- no need to re-mention me.

"Already resuming" stays quiet: another worker is about to post the
continuation.

## A card blamed a segment that was granted (#264, partly)

Cards carried the classifier's verdict on the **whole command** rather than the
grant layer's account of the segment it would not vouch for. Those differ on
anything compound, because the classifier reports the verb it stopped at:

    command:  git log --oneline && frobnicate
    before:   card said "git log: no rule"
    after:    card says "frobnicate: no rule"

`git log` is granted outright, so the card described a refusal that had not
happened.

**The cost was not only confusion.** The agent explaining such a card to its
approver invented a rule to fit it — *"git reads have no standing rule in the
main checkout, only worktrees"* — which this codebase does not have. A
misleading message got restated as fact to the person being asked to approve.

A classifier *refusal* still reports the classifier's own grounds, so #172's
"a refusal is not a question" keeps its wording.

## `git merge-base` reads (#264, partly)

No writing form: `--is-ancestor`, `--fork-point`, `--octopus`, `--independent`
and `-a` only change what it answers. Its absence cost a card — and because a
combined read parks if any one part does, it took every other segment of the
command with it.

## Still open on #264

Two larger gaps are deliberately not in this release: command substitution is
refused wholesale even when it holds only granted reads, and `cat >` heredoc
writes inside the tree still park in an unattended channel. Both are riskier
than the two above and want their own change.

## Checks

`selfcheck.py` checks 59 and 60. Check 59 covers the park-time thread, the
race, the non-overwrite with its warning, and the unattributed card blocking
its channel. Check 60 covers five `merge-base` forms, the compound refusal
naming the right segment, the classifier refusal keeping its own grounds, and
that the card scrubs a reason quoting a credential — the last asserted with a
real detector rather than a pass-through, because a pass-through would pass
while measuring nothing.
