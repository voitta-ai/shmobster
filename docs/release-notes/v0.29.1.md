# shmobster v0.29.1

One fix: a failure is attributed to one waterfall rung, or to none -- never to
the wrong one. The rest is documentation.

## What an upgrade requires

Nothing. No new config key.

One new startup line is possible. If two waterfall rungs share a `model`, boot
now logs

    config: waterfall rungs <a>, <b> all use model '<model>', so a failure
    cannot be attributed to one of them and none will be parked -- give them
    distinct models

That configuration was already behaving this way; the warning is new, not the
behaviour it describes. Giving the rungs distinct models clears it.

## A failure parked the wrong rung (#289)

`llm._vendor_for` has two ways to identify the vendor behind a failure, and
they disagreed about ambiguity. The suffix branch collected every match and
refused to act on more than one. The exact branch -- the preferred one, matching
`litellm_params.metadata.deployment` -- returned the first hit.

Two rungs may legitimately share a `model` and differ only in `api_key` or
`api_base`. The same model on two accounts, for rate limits that throttle
independently, is a normal reason to add a fallback, and the README's free-tier
section effectively recommends that shape. When they do, every failure was
attributed to whichever rung was listed first -- so a failure on the second
parked the first, taking a *working* rung out of the chain. That is the outcome
`_vendor_for`'s own docstring calls worse than not parking at all.

Measured on two rungs both holding `gemini/gemini-flash-latest`:

| path | before | after |
|---|---|---|
| exact (`metadata.deployment`) | `'gemini'` | `None` + warning |
| suffix (provider + `endswith`) | `None` + warning | `None` + warning |

A rung with a unique model resolves to its own name exactly as before.

The guard only speaks once something has already failed, so `config.py` gains
`waterfall_warnings()`, logged at startup beside the secret warnings: a
waterfall carrying duplicate models says so at boot rather than degrading
quietly at the first 429. It names models and never keys -- two rungs differing
only in `api_key` is precisely the configuration it reports on.

## Documentation

**Configuring an org-hosted OpenAI-compatible gateway (#287).** Three things
that are not guessable, and one probe that lies. The base URL may be an
organisation's own deployment rather than the vendor's public host, and a key
valid against one returns `403 Invalid authorization token` against the other --
indistinguishable from a revoked key, so probing the wrong host sends you off to
rotate a key that was fine. The litellm model string needs the `openai/` prefix
*and* the full gateway model id; without the prefix litellm resolves
`anthropic/...` to Anthropic directly and ignores `api_base`, so a routing
mistake surfaces as an auth error. A header another client needs (Codex CLI's
`X-Title`) is not required here, which matters because a waterfall entry has no
header field.

And `GET /v1/models` is not a credential check. It returns 200 for a garbage key
on one gateway and 403 on another, so it is wrong in two different directions;
`POST /v1/chat/completions` is the only call that answers on both, and its
`400 Invalid model ID` is the cheapest positive proof a key is live.

**A gateway route can drop an image and answer anyway (#287 follow-up).** Vision
is a property of the route, not of the gateway. Measured with a solid-colour PNG
and a three-colour control, `anthropic/claude-haiku-4-5` and
`vertex/gemini-2.5-flash` scored 3/3 while `openai/gpt-4.1-mini` scored 0/3 --
answering `Blue` for red, `Yellow` for blue and `Red` for yellow, with no error
and nothing in the response saying an image was removed. One wrong answer would
not have shown it, which is why the documented control is three distinct images
checked for tracking. It is not "Claude only": a `vertex/` route passed where an
`openai/` route did not.

## Packaging

`.gitignore` matched `shmobster-config.json` exactly, so a backup beside it --
`.bak`, `.orig`, a dated copy -- was untracked *and* unignored, one `git add -A`
from committing live credentials to a public repo. Hit for real while doing the
#231 remediation on a live box. Both that file and `shmobster-policies.json`
now ignore their backups; a per-channel policy `env` value is a credential too.
