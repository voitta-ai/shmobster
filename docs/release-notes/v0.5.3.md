A bug fix. Every command's disposition is now on the record, not only the ones
that got parked.

## What ran, what was blocked (#97)

v0.5.2 gave the approval queue a log: `approvals: parked [id] ...` and
`approvals: claimed [id] ...`. Commands that actually **ran**, and commands
**blocked by channel policy**, still logged nothing -- the same audit hole
v0.5.2 was about, in the half that was left open.

Found the way these always get found. An agent was asked about a link, said it
could not see the content, and asked a human to go read it instead. Whether it
had tried and been blocked by the channel's `github_repos` whitelist, or never
tried at all, turned out to be unanswerable: two turns ran in that window and
the log had no line from either.

Those two have opposite fixes. Blocked means the block message needs work;
never tried means the tool surface does. Guessing between them is exactly what
made the previous investigation take an hour.

Now, from `execute()` -- the choke point both the auto-run path and the
approved path pass through:

    approvals: parked [3] in C0... (mutating): 'gh issue create ...'
    approvals: claimed [3] in C0...: 'gh issue create ...'
    run_shell: running: 'git log --oneline -5'
    run_shell: exit 0: 'git log --oneline -5'
    run_shell: blocked by policy ("repo 'x/y' not in channel whitelist ['a/b']"): 'gh repo view x/y'

Logged before the subprocess as well as after, so a command that hangs to the
timeout, or one in flight when the watchdog (#66) restarts us, still leaves a
trace. The exit line repeats the command rather than relying on adjacency:
Bolt handles events concurrently and two turns interleave.

## Two things the log had to survive to be worth having

**A command cannot forge a line in its own record.** Written as `repr`, so a
command carrying a newline cannot emit what looks like a second entry -- an
`exit 0` for something that never ran, or a `blocked by policy` covering one
that did. An audit trail writable by the thing it audits is not one. The two
`approvals` lines from v0.5.2 had the same shape and got the same treatment.

**Everything on the line is scrubbed, not just the command.** Redaction happens
at the emission site rather than through the formatter the Slack ingest
installs at boot (#72), because `tools` and `approvals` are reachable without
that bootstrap. That has to cover every field, and three of them get the
command back by another route:

- `subprocess.TimeoutExpired` renders as `Command '<cmd>' timed out after Ns`.
- The policy reason quotes the command back: the aws guard names the
  `--profile` value it rejected, the exclude guard names the offending path.
- `yolt_gate` renders its own failures as `yolt error: <exc>`, and a timeout
  there carries the classifier's argv -- the command, again.

Every argument in every line is now either scrubbed and `repr`'d, or has no
command-derived content at all (request id, channel id, exit code).

## Upgrading

    git pull
    .venv/bin/pip install -r requirements.txt
    .venv/bin/python selfcheck.py
    deploy/service.sh restart

- **Nothing to change.** No new config key, no new dependency.
- **The log gets busier.** One or two lines per shell command, at INFO. Worth
  knowing before it surprises you in `deploy/service.sh logs`.
- **The restart clears the approval queue**, as every restart does.
