Three fixes around the approval surface: a click that acknowledges itself, a
refusal that says what to do next, and per-channel `env` that can finally hold a
`${VAR}` instead of a pasted secret.

## The Approve button says something now (#101, #102)

A trusted user clicked **Approve**, saw nothing happen, waited half a minute,
and asked for the same request by name -- by which point it had already run:

    09:47:48.813  approval card posted
    09:47:5x      user clicks Approve
    09:47:56      card rewritten in place with APPROVED + output
    09:48:25      user types "approve 4"   <- 29s after it had already run

The click worked. One `claimed`, one `running`, one `exit 0` in the log; nothing
ran twice. Only the feedback failed, for three reasons. `chat_update` is silent
-- editing a message produces no notification, no unread marker, no scroll, so a
card rewritten in place is invisible unless you happen to be looking at it. The
card also sat untouched for the whole command, buttons live, because the handler
acked, ran, and only then touched the message; this one hit a network API. And
the agent's own reply above the card still said a trusted user could say
"approve 4", long after the card had resolved -- two messages describing one
request, only one of which ever updates.

The card is now rewritten twice: once on the click, with the buttons gone, the
claimer named and the command still readable, and again with the result.

That the buttons come off immediately also closes a race. Approve pops the
request and *then* executes, so a second click during a slow command found
nothing pending and overwrote the real output with an error about a request that
had run. Underneath, the queue is now properly synchronized: `pop` looked the
request up and deleted it in two steps, so a button click and a text `approve 4`
arriving together could both pass the guard and one would raise `KeyError` out
of a handler; `claim_unsurfaced` iterated the queue while other threads mutated
it. Every read and write takes one lock, an in-flight request is held for the
duration, and queue overflow never evicts one.

Log lines also carry timestamps now (#102). Reconstructing the sequence above
meant correlating the disposition log (#97) against Slack with nothing on the
log side to correlate with -- `basicConfig` had no `format`.

## A refused click says what to do next (#107)

An untrusted Approve click already left the card and its buttons standing and
tagged the trusted users (#94). It never said so, though: "only trusted users
may act on a parked command" states a rule, and a reader takes from it that the
click consumed something. In the thread that prompted this, the next message
asked the agent to re-raise a request that was sitting right there, still
clickable.

Now it distinguishes three states, because they want three different answers.
Still parked: the request is parked and the Approve / Deny buttons on the card
above are live, so a trusted user can act on it there. In flight: a trusted user
is already acting on it. Gone: no longer pending here.

Telling those apart is less obvious than it looks. A trusted click acquires the
request and strips the buttons *before* the approve path pops it, so the queue
reports "pending" early in that window and "gone" for the entire duration of the
command -- and neither is the useful answer. Only the hold spans it. All three
come from one locked snapshot, so the message can go stale on the way to Slack
but can never be self-contradictory.

## `${VAR}` in the policy file (#104)

`_load_policies()` was a bare `json.load` while the main config was
interpolated, so a per-channel `env` value could only be a literal secret -- the
one place in the deployment where a credential had to be pasted in.

    "env": { "FIGMA_TOKEN": "${FIGMA_TOKEN}" }

This is what makes per-channel `env` usable as the scoping mechanism it was
meant to be, and it needed a second fix to actually be one. A `${VAR}` has to
exist in the process environment to expand, and every subprocess starts from a
copy of that environment -- so moving a token from a literal to a reference
would have published it to every other channel, readable with `printenv`. Names
claimed by any channel's `env` are now stripped from the inherited copy and
added back only for the channel that declares them.

Worth knowing for a related reason: a command that reads its credential from the
environment does not need to `source` anything, and without the `source` it is a
plain read-only command that never trips the mutating gate. A per-channel token
removes a whole class of approval prompt.

Writing a policy is safer too. `set_policy` validates the merged document before
persisting it -- since the file can hold `${VAR}`, a write whose reload was then
rejected would leave the agent on the old envelope and the next boot dying on a
file the agent itself wrote. Writes go through a temp file created with the
original's mode and renamed, so a crash cannot truncate the live policy file and
a rewrite cannot widen a `chmod 600` file holding credentials.

## Known, not fixed

**#109 -- an approval card from before a restart can approve a different
command.** Request ids are a process counter that restarts at 1, while cards are
Slack messages that outlive the process and carry only that short id. Click an
old card after a restart and the queue may hand back whatever reused the id. The
human approves what they read; something else runs. Pre-existing since #50, and
restarts are frequent because the #66 watchdog exits on a wedged socket. It
wants a unique per-request identity.

## Upgrading

    git pull
    .venv/bin/pip install -r requirements.txt
    .venv/bin/python selfcheck.py
    deploy/service.sh restart

- **Nothing to change.** No new config key, no new dependency.
- **If you move a policy `env` value to `${VAR}`**, the variable has to reach
  the *service* environment, not just your shell: launchd does not read
  `~/.bash_profile`, and a `launchctl setenv` after the service was bootstrapped
  does not reach an already-running process. Set it, then reload the service.
- **The restart clears the approval queue**, as every restart does.
