## What actually goes wrong with launchd env vars (#111)

The config section already carried a macOS caveat: launchd does not read
`~/.bash_profile`, so put your `${VAR}` values in the launchctl environment or
the plist. All true, and it still cost a full debugging cycle on a live
deployment, because the three ways it goes wrong are each invisible and each
looks identical to "the variable is missing".

**A running service does not see a later `setenv`.** Its environment is a
snapshot taken when the service was bootstrapped. `launchctl kickstart -k` --
which `deploy/service.sh restart` uses -- restarts the process but reuses the
loaded definition, so the new variable is still not there. Getting one into a
running service needs `bootout` + `bootstrap` (`deploy/service.sh update`).
What the service actually holds is readable:

    launchctl print gui/$(id -u)/ai.shmobster.agent | sed -n '/environment/,/}/p'

**`launchctl getenv` exits 0 whether or not the variable is set.** So the
obvious check answers "present" for everything:

    launchctl getenv SOME_VAR >/dev/null && echo present    # always "present"

Measure the output instead -- `launchctl getenv SOME_VAR | wc -c`, where 0 bytes
means unset. This one is worth internalising: acting on that exit code produced
a confident, wrong answer about where a token was, and the correction cost a
bootout/bootstrap cycle to establish.

**A sync tool that greps `^export` out of one profile misses sourced files.** If
`~/.bash_profile` does `. ~/.bash_profile_extra.sh`, a text scan of the first
file never sees what the second defines, and those variables silently never
sync. On the machine where this came up that was 81 of 176 exported variables.
Compare `grep -c '^export' ~/.bash_profile` against
`bash -lc 'compgen -e' | wc -l`; if they disagree, deriving the list from the
live login environment rather than from a file is the fix.

The caveat also used to describe osx-env-sync as syncing "`~/.bash_profile` ->
launchctl", which is exactly the description that makes the third case
invisible. That claim is gone.

## Upgrading

    git pull
    deploy/service.sh restart

Nothing to change, and nothing in the running agent behaves differently -- the
only reason to restart is to leave the deployment on the released commit.
