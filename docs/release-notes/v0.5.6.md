One fix, on the approval gate. No config change, no new dependency -- but the
approval ids you see in Slack look different, and the ones on cards posted
before the upgrade stop working.

## An approval card from before a restart could approve a different command (#109)

A request's id was a process counter starting at 1. An approval card is a Slack
message: it outlives the process, keeps its buttons, and shows its id long after
the queue that issued it is gone. Restarts are routine -- the #66 watchdog exits
on a wedged socket and the supervisor brings it straight back -- so the same id
was handed out again, to a different command:

1. Request [4] is parked in a channel; nobody acts on the card.
2. The process restarts.
3. New work parks a fresh request, also called [4].
4. A trusted user scrolls up, reads the **old** card, and clicks Approve.
5. The queue finds the new request and runs it.

The human approved what the card showed them; something else ran. Both the
channel scope and the trust check are satisfied throughout, so neither catches
it -- and it is the one property the approval gate exists to provide. This had
been true since #50 put the id in the button value; it was listed as "Known, not
fixed" in v0.5.4.

**The id is now unique per boot:** a counter prefixed with a nonce drawn fresh at
every start and never persisted, so a card from a previous boot matches nothing
and is answered with "no longer pending in this channel".

    :lock: Needs approval [a1b2c3d4e5f60718-3] (mutating)

The nonce is on the id every surface *prints*, not only on the value the button
carries. A stale card still shows its number, and typing that number is the
documented fallback for when the buttons are not available -- so a bare
`approve 3` completed into "this boot's 3" would rebuild the same failure with
the click replaced by a sentence. A bare number therefore resolves to nothing.
Quote the id as the card shows it; one layer of the surrounding brackets comes
off, so pasting `[a1b2c3d4e5f60718-3]` works.

When an id resolves to nothing, the answer says how many requests are parked
here, never which. That reply is another turn in the agent's tool loop, so a live
id in it is an id the agent can approve on its own initiative, for a command no
human quoted -- the same boundary from the other side. The count is there so
"no pending request" does not read as "your request was consumed" (#107).

The refusal dedupe for unauthorized clicks is keyed on the same id. It was keyed
on the bare number, so a stale click on [4] silenced the alert for a genuinely
live [4] afterwards -- hiding exactly the click trusted users are meant to hear
about.

## Upgrading

    git pull
    .venv/bin/pip install -r requirements.txt
    .venv/bin/python selfcheck.py
    deploy/service.sh restart

- **Nothing to change.** No new config key, no new dependency.
- **Approval cards posted before the restart stop resolving.** That is the fix
  working. Any request parked before the restart is gone with the queue anyway
  -- it was always in-memory only -- so re-ask for the command; the old card's
  buttons now say so instead of running something else.
- **Ids are longer.** `a1b2c3d4e5f60718-3` rather than `3`, in the card, in the
  log lines, and in what you type. The nonce is 64 bits because a repeat is not
  a cosmetic clash here: it is a dead boot's card resolving to a live request
  again.
