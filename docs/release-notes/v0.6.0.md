Three changes to what a command may do, all in the exec path. Two new policy
keys, one behaviour you will notice on the first commit, and one operator action
for channels that use an AWS profile.

## Every command runs inside a sandbox (#116)

`cwd` used to be the working directory and nothing more: an absolute path
elsewhere, a symlink inside the tree pointing out of it, or a path the shell
resolved at runtime all went through, for reads and for writes. The `exclude`
guard said in its own docstring that it was not a sandbox.

Every command now runs under macOS `sandbox-exec` with a seatbelt profile built
per channel from its policy. Writes are confined to the channel `cwd`, its
sibling `<cwd>.worktrees/`, the temp dir, `/dev` and three toolchain caches.
Reads are denied under `/Users` and `/Volumes` -- every home, `/Users/Shared`,
every mounted drive -- except the tree, those caches, and what git and gh read
on every call. The policy's `exclude` paths are denied last, so they win. The
kernel decides on the resolved path, which is what makes a symlink unable to
escape. Fail closed: no `sandbox-exec`, no command.

Two new per-channel keys, `allow_read` and `allow_write`, add paths beyond that
-- a data directory next to the project, say. Never a credential: a file a
channel can read, a read-only `cat` posts into Slack without a card. The
allowances are per channel on purpose; there is no global form.

## In-tree writes and your own commits no longer wait for a card (#117)

YOLT answers *does this mutate anything*, and every yes parked for a human --
including `cp x app/index.html && git add ... && git commit ...` inside the
channel's own worktree. A mutating command now runs without a card when every
segment is YOLT-safe, a filesystem verb the sandbox confines to the tree, a
local git write (`add`, `mv`, `stash`, `checkout -b`, `switch -c`), or
`git commit` in a *linked worktree* on a *non-default branch* whose commits so
far are all yours -- the predicates from voitta-yolt's closed #82, which YOLT
itself will never apply now that it is deny-only. A redirect on any of those
(`cat > f <<'EOF'`) counts as an in-tree write.

It is an allowlist: `rm`, `git reset`, `git clean`, `git restore`, `git push`,
`gh`, `aws`, `sudo` still card. The command is walked as a bash AST; a subshell,
a `$(...)` in an allowlisted verb's arguments, a `FOO=1 cmd` prefix, or a `cd`
that cannot be resolved statically is refused rather than guessed at. Every grant
is logged with its per-segment grounds next to the park and claim lines.

## Git talks to GitHub over https, and `~/.ssh` is never readable (#122)

The first draft of the sandbox told a channel that pushes over ssh to grant
`~/.ssh`. That hands a read-only `cat ~/.ssh/id_*` to the no-card path; denying
the directory breaks `git push`. Neither, and ssh was never needed: four git
config entries injected into every command's environment send `git@github.com:`
remotes over https with the token `gh` keeps in the keychain, and consult only
`gh auth git-credential` -- the system-wide `osxkeychain` helper Homebrew
configures hangs inside the sandbox on a keychain prompt. Per process; your
own `~/.gitconfig` and remotes are untouched. Startup warns if this host's git
predates 2.31 or `gh` is not logged in, and denies `~/.config/gh/hosts.yml` to
every channel if `gh` keeps its token there instead of the keychain.

The rule behind all three: a secret never enters a channel through a readable
file -- keychain, agent, or the channel's own `env`.

## Upgrading

    git -C /path/to/voitta-yolt pull
    git -C /path/to/skillz pull
    git pull
    .venv/bin/pip install -r requirements.txt
    .venv/bin/python selfcheck.py
    deploy/service.sh restart

- **macOS only, fail closed.** The sandbox is `sandbox-exec`; on a host without
  it no command runs. `selfcheck` proves the confinement live where it can.
- **`aws_profile` channels need their keys in `env`.** `~/.aws` is not readable
  -- its credentials file holds every profile's keys -- so a channel that used
  `aws_profile` alone now fails on the first `aws` call. Give it
  `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and `AWS_DEFAULT_REGION` through
  the policy's `env` as `${VAR}` references (#104), and export those variables to
  the service's environment. Keep or drop `aws_profile` as you like; with keys in
  the environment the CLI does not consult the profile for credentials.
- **`exclude` entries are now enforced in the kernel** as well as textually, and
  a relative entry resolves against the channel `cwd`.
- **`~` is not readable from a channel** beyond the tree, the toolchain files and
  `allow_read`. If a channel's work needs a directory under your home, list it.
- **Branch worktrees go in `<cwd>.worktrees/`.** That sibling is part of the
  tree; a worktree anywhere else is outside the sandbox and outside the grant.
- **git >= 2.31 and a logged-in `gh`** on the host, with the token in the
  keychain (`gh auth login` does this where a keychain exists). Startup logs a
  warning otherwise.
