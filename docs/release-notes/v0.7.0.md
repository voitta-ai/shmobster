One feature in two halves: the agent can learn, and every gate you already
trust decides what that means. One new config block, one new policy key, and
nothing changes until you set them.

## The agent flags; you decide; a merged PR is the skill (#129)

Every channel turn is now recorded -- the request, each tool call with its
disposition (ran / parked / blocked / approved), the answer -- one scrubbed
JSON line per turn under a gitignored `trajectories/` dir.

When a turn met the bar (non-obvious debugging, a workaround found by trial
and error, a quirk the docs do not cover), the agent may call `flag_skill` --
once per thread, and only where `learning.repo` is configured. The reply is
followed by a card tagging the trusted users:

    :bulb: Worth a skill? [a1b2c3d4e5f60718-2] `launchd-bootstrap-race` -- <why>
    [ Open PR ]  [ Decline ]

A trusted click on **Open PR** drafts a skillz-format `SKILL.md` from the
thread's own record and opens a PR against `learning.repo` at
`channels/<channel>/skills/<name>/` -- through `gh api` from the agent
process, never from a channel shell, so the model has no push path to the
skills repo. **Decline** records the thread and it is not asked again. Text
works too: `propose <id>` / `decline <id>`, trusted users only, the same
refusal on an untrusted click as an approval card. Transient failures keep
the proposal id and re-render the card; a retry resumes a part-made PR
instead of making a second branch.

Merging the PR is the promotion. Nothing loads before a human merges.

## A channel loads its own skills (#130)

A channel policy may carry `skills`: directories of `<name>/SKILL.md` that
channel alone sees, on top of the global `skills.paths` (global wins a name
collision). That is where the merged PR lands, so the loop closes: flag ->
card -> PR -> merge -> `git pull` the catalog clone -> on the menu, in that
channel only. Channel dirs are read per turn, so a merge or a `set_policy`
edit shows up without a reload.

One rule is enforced: a `skills` entry that resolves under the channel's
writable roots (the tree, its worktrees sibling, temp, the caches,
`allow_write`) is ignored with a warning. In-tree writes run without a card
since v0.6.0, and a granted write must not become next turn's standing
instructions -- the write roots come from the same code the sandbox profile
is built from, so the check cannot drift from the kernel.

A loaded skill carries no authority either way: it is prompt text, and its
commands go through the same YOLT / grant / sandbox / approval path as
anything else.

## Upgrading

    git -C /path/to/voitta-yolt pull
    git -C /path/to/skillz pull
    git -C /path/to/skillz-private pull    # learned skills land there
    git pull
    .venv/bin/pip install -r requirements.txt
    .venv/bin/python selfcheck.py
    deploy/service.sh restart

- **Off by default.** No `learning` block in the config -> no flag tool, no
  cards, nothing new in the prompt. Trajectory recording is on regardless
  (local, gitignored, scrubbed).
- **To turn it on:** `"learning": {"repo": "<owner>/<private-skills-repo>"}`
  in `shmobster-config.json` (optional `base`, `path`); a `skills` entry in
  each channel's policy pointing at that repo's local clone,
  `channels/<channel>/skills` -- outside the channel tree, or it is refused.
  `gh` must be logged in on the host, which git-over-https (v0.6.0) already
  requires.
- **New files on disk:** `trajectories/` next to the logs; add it to any
  backup exclusions if you have them.
