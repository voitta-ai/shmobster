One fix on the approval gate and two rules in the agent's spine. No config
change, no new dependency.

## A text approval racing a click no longer contradicts the card (#105, #138)

The in-flight hold was advisory: a button click acquired a request but left it
in the queue, so a trusted user typing `approve <id>` during the run popped and
ran it -- and the click's own path then rewrote the card to `no pending
request` for a command that DID run. One execution, two surfaces telling the
thread opposite stories.

Ownership now moves with the request: the moment any surface takes it, it
leaves the queue, and every other surface -- the other delivery of the same
click, a typed approval, a typed deny -- is told

    [<id>] is already being acted on by another surface -- do not retry;
    that surface will report the outcome.

Exactly one consumer ever gets a request; a surface that fails mid-flight puts
it back pending rather than consuming it, and a refused click during a run can
now name the command it did not run. The skill-proposal queue (#129) follows
the same rule.

## Claims follow evidence (#134, #137)

From a live incident: the agent stated repo facts while its verifying command
sat parked for approval, and promised a preview URL it never checked while
both downstream deploys failed. Two spine rules now say: facts whose verifying
command is parked are reported as "parked, awaiting approval", not asserted;
and an outcome the agent promised (a push's preview URL, a PR's checks, a
deploy) is verified -- `gh run list/watch`, `gh pr checks`, fetch the URL --
and the verified state reported in-thread, failures included.

## Upgrading

    git pull
    .venv/bin/pip install -r requirements.txt
    .venv/bin/python selfcheck.py
    deploy/service.sh restart

Nothing to change. Approval ids, cards and the text fallback all work as
before; the only visible difference is the "already being acted on" answer
where you previously might have seen a false "no pending request".
