This release reverses an instruction the last one gave. v0.8.0 said, in these
notes and at startup, that **voitta-yolt 2.0.0 is not supported** and an
operator who upgraded into it should know why it was the wrong version. That
was right at the time and it is wrong now: the supported range is **`>= 2.0.1`**,
and a deployment left on 1.6.0 will refuse to run.

Read **What an upgrade requires** before upgrading. As with v0.8.0, an upgrade
that skips it does not fail loudly -- it changes what a channel can do without
saying so.

## What an upgrade requires

**1. Upgrade voitta-yolt to `>= 2.0.1` (#177, #182).**

The previous floor was `>= 1.6.0, < 2.0.0`. Both ends moved.

v0.8.0 held off 2.0.x because it collapses "we deliberately delegate this" and
"we could not classify this" into one `unknown` verdict, so every ordinary read
in a channel parked for a card. That hold was waiting on voitta-yolt#144 to
separate the two. **It cannot be separated.** `rules/shell.json` states that
delegation is the *absence* of a rule, so `cat` and a command YOLT never heard
of are the same answer, upstream cannot tell them apart either, and a fix would
mean restoring the list 2.0.0 deleted.

So the read-only set moved here, as `grant.READ_VERBS` and its git/gh/aws
companions. It is consulted only when YOLT says `unknown` -- never over
`unsafe` or `deny`, so it can promote and never override.

The floor is 2.0.1 rather than 2.0.0 because `--cwd` arrived there. Without it
2.0.x's `deny` verdict is evaluated against whichever directory the agent
process happens to be in rather than the channel's, which fails in both
directions and announces neither.

Startup enforces this rather than trusting a pin. The probe asks about a
command no version has ever called anything but unsafe:

    grammar_classifier.py --no-user-allow --cwd / 'rm -rf /tmp/probe'   # expect "unsafe"

A classifier predating `--cwd` takes the flag as the command and answers about
the flag string, never looking at the `rm`. That is why the probe is not a
version check: the version string would have passed.

**2. Add `slack_channels` to any channel that posts or reads elsewhere (#151).**

`slack_post`, `slack_read_thread`, `slack_read_channel` and
`slack_read_permalink` took an arbitrary `channel_id` straight to the Slack
client -- past `policy.check`, past the grant layer, past the approval card. The
agent could read any channel the bot belongs to and post, or `<@mention>` a
user, into any of them, with nobody in the path.

They now reach **this channel only**, unless the channel's policy names others:

    "slack_channels": ["C0123456789"]

Omit the key and cross-channel reads and posts are refused. If a channel's
normal work includes posting into another one, this is the key that keeps it
working.

**3. A channel that writes git hooks or `.git/config` will now fail (#184).**

`.git/` is not data, it is configuration git executes. The grant layer vouches
for an in-tree write on the verb alone and `.git/` is in the tree, so
`tee .git/hooks/pre-commit` plus `chmod +x` plus `git commit` -- three commands
it already grants -- ran arbitrary code with no card.

The sandbox now denies `file-write*` on `.git/hooks/`, `.git/config`, the same
paths under `.git/modules/<name>/` for submodules, and `config.worktree`.
Everything else under `.git/` stays writable, because `git add` and `git commit`
are granted and have to write `index`, `objects` and `refs`; `git worktree add`,
`stash`, `gc` and `fetch` are all unaffected.

## What changed that is not a fault

**Ordinary reads auto-run again**, which is the whole point of the yolt work:
`cat`, `ls`, `grep`, `head`, `git status`, `git log`, `git diff`, `gh pr list`,
`gh pr view`, `aws s3 ls` and the `list-`/`get-`/`describe-` operations.

**And the read set is deliberately narrower than voitta-yolt 1.6.0's**, which
is the surprising half. Measured against that tag, every one of these
classified `safe` -- auto-run, with no card:

    git branch -D <branch>          deletes a branch
    git remote add o <url>          mutates the repository's config
    git config user.email x@y       mutates the repository's config
    gh api repos/<owner>/<repo>     reaches any repo the token reaches

They now ask first. So do the AWS operations that hand back credentials --
`secretsmanager get-secret-value`, `ecr get-login-password`,
`sts get-session-token`, `ssm get-parameter` -- which do not mutate anything
here but put secret material into a channel, where the redactor cannot help: a
bare token has no shape to catch. That is the same argument #149 made about a
fetch being read-only here and an effect out there.

`git grep` asks first too, because `git grep -O<cmd>` runs the pager it is
handed. Plain `grep` covers the use and carries no such flag.

**`git -c` and `--config-env` are refused entirely**, for local writes as much
as reads. `-c diff.external=CMD` with `git log -p --ext-diff`, and
`-c core.fsmonitor=CMD` with `git status`, both execute CMD with stdout a pipe.

## Also

- A rejected classifier invocation now reports its own reason. voitta-yolt
  signals errors out of band -- non-zero exit, message on stderr, stdout empty
  -- so an operator used to see `Expecting value: line 1 column 1 (char 0)`
  where the real event was a refusal with a named cause.
- `docs/NEW-MACHINE.md` is rewritten. Its central warning used to be "do not
  upgrade voitta-yolt past 1.6.0" and now says the opposite, so it names the
  reversal explicitly for anyone working from memory or from a machine set up
  before 2026-09-16.

## Known and open

- **#186** -- TMPDIR is a writable root, so a channel can `git init /tmp/x`,
  write a hook there and commit, reaching what #184 closed by another door.
  This is also why #184 leaves a worktree's `.git` pointer file writable:
  denying it breaks `git worktree add` and buys nothing while that stands.
- **#150** -- `github_repos` remains a best-effort text guard rather than a
  gate. `gh api` reaches any repo the token reaches.
- **#152** -- no lockfile or hashes; `aiohttp` and `litellm` are stale.
